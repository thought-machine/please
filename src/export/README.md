# Package export

This package implements the `plz export` command, which extracts a subset of targets and their
transitive first-party dependencies from a Please repository and packages them into a standalone,
self-contained Please repository. This is useful for separating modules, distributing sub-projects,
or creating minimal reproducible workspaces.

---

## High-Level Architecture

The entry point to the export process is the `Repo` function in `export.go`. It orchestrates the
export by running common export steps and invoking the appropriate export implementation based on
the user's requirements.

The architecture is separated in:

1. **`baseExporter` (`export.go`):** Common orchestrator that manages shared state (such as the
   target output directory, build state, and tracking of visited targets) and handles copying
   configuration files (`.plzconfig*`, `.gitignore`) and first-party source files.
2. **`exportStrategy` Interface:** Abstract interface implemented by two distinct export strategies:
   - **No-Trim Exporter (`noTrimExporter`):** Preserves the full packages.
   - **Trimmed Exporter (`trimmedExporter`):** Prunes `BUILD` files to only include the necessary
     statements and targets.

---

## Export Strategies

Depending on whether `--notrim` is specified, Please employs one of the following two strategies:

### 1. Trimmed Exporter (`trimmed_exporter.go`)

This is the default strategy. It dynamically prunes the `BUILD` files of any visited packages so
that the output files contain only the declarations, subincludes, and targets that are strictly
required by the exported target(s).

- **Adjacent Targets:** When exporting a target, the trimmer identifies any other
  targets declared within the exact same statement (e.g., adjacent targets created by a single build
  definition call) and preserves them to prevent syntax and reference issues.
- **AST-Based Trimming (`trimmer.go`):** Parses the package's original `BUILD` files using Please's
  ASP interpreter and systematically walks the abstract syntax tree (AST) block-by-block. Unneeded
  build targets and unneeded `subinclude` arguments are removed. Crucially, variable assignments and
  other non-target-generating statements (e.g., `package()` calls) are completely preserved to
  guarantee the resulting `BUILD` files remain syntactically and semantically valid.
- **Control Flow Preservation:** Trimming preserves `if-else` and `for` loop structures. Branches
  that contain required statements are kept and trimmed, while inactive branches are cleanly stubbed
  with `pass  # Trimmed during export` to keep the syntax tree valid.

### 2. No-Trim Exporter (`notrim_exporter.go`)

Used when `--notrim` is passed. This strategy preserves the complete structure and original contents
of any visited packages:

- Visited packages copy their original `BUILD` files intact directly to the destination.
- All package and transitive targets, preloaded definitions, and source files are exported.
- No pruning or modifications are made to the `BUILD` files.

## Statement Tracking & Package Metadata

To support trimming, Please tracks rich package-level metadata during the initial parse phase.


### Metadata Registration (`core/package_metadata.go` & `parse/asp/interpreter.go`)

As the parser processes a `BUILD` file, it registers metadata in `PackageMetadata` representing all
statement details:

- **`RegisterTargetStatement` / `RegisterStatement`:** Maps each generated build target back to its
  corresponding AST statement, along with files and required subincludes.
- **`FindTargets` / `IsInterpretedStatement`:** Allows the trimmer to find which targets were
  generated by a given statement, and verify if a statement inside an `if` block was interpreted or
  not.
- **`FindPackageLevelRequirements`:** Identifies any subincludes or files needed for package-level
  variable declarations or global expressions, ensuring these are preserved even if they don't
  belong to any target.

### Upfront Parsing

To support package-level trimming, the exporter must have access to metadata for adjacent targets
that normally (e.g., during a standard build operation) would not be parsed or resolved.

For this purpose, Please utilizes an upfront-parsing model. When `ForceParseEntirePackage` is set to
`true` during the parse phase, the interpreter synchronously parses and resolves all targets in any
visited package upfront. This guarantees that all package-level statement and target metadata is
fully populated and available, eliminating the need for any dynamic or lazy parsing during the
export phase.
